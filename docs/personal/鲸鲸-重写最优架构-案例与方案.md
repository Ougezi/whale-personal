# 如果重写鲸鲸：最优架构、边界与案例

> 版本：v1.0（架构决策稿）
> 日期：2026-11-24
> 对象：鲸鲸个人版 4.9（Launcher → Kernel 8787 → Bridge → DSH）
> 结论：**不建议推倒重写；建议“保留外壳 + 重画四条边界”的 2.0 重构。**

---

## 0. 一句话结论

**最优方案不是“把 32,000 行内核换成新框架”，而是：**

> 保留 Launcher、UIA 桥接、人设/提示词资产、现有安全守卫；  
> 重画 **记忆、能力、通道、插件** 四条边界；  
> 用“事件日志 + 投影 + 动作注册表 + 通道适配器 + 插件契约”替换散落的直接写盘和隐式触发。

预计：

- 保留约 **60–70%** 代码/资产；
- 重写/新写约 **30–40%**；
- 分 5–6 个阶段，约 **8–12 周**（单人 + AI 辅助，不含长期观察）。

---

## 1. 为什么不做“大一统重写”

| 方案 | 风险 | 判断 |
|---|---|---|
| 全部推倒，换语言/框架 | 丢失 UIA/微信兼容、人设资产、记忆数据、边界守卫；回归面巨大 | ❌ 不建议 |
| 全量微服务化 | 本地单机应用，增加部署/调试/跨进程一致性成本 | ❌ 过度设计 |
| 换 Electron/Web 重做 UI | 与核心问题无关，现有 WPF 能用 | ❌ 低收益 |
| **模块化单体 + 四条边界重构** | 可控、可灰度、可回滚 | ✅ 推荐 |

鲸鲸的关键资产不是“代码行数”，而是：

1. 微信 UIA/DB 兼容经验；
2. 人设/提示词/口吻；
3. 真实记忆数据；
4. 已经踩过的安全/稳定性坑；
5. 主人自己的使用习惯。

这些都不该在重写中丢掉。

## 2. 现状：哪些是好的，哪些必须改

### 2.1 保留

| 资产 | 原因 |
|---|---|
| Launcher（WPF） | 启停/配置/日志/诊断已经可用，重写收益低 |
| Bridge（Python + wechatauto/UIA） | 微信 UI 自动化的兼容经验最贵 |
| Kernel HTTP（8787） | 本地单进程简单可靠 |
| Persona/prompt 静态块 | 2,389 tokens 的稳定资产，前缀缓存 |
| 记忆数据 | 原文/人物卡/摘要/事件是长期积累 |
| brain_policy/审计/确认 | 已有 R0–R3、路径/网络、审批 |

### 2.2 必须改

| 问题 | 现状 | 2.0 目标 |
|---|---|---|
| 记忆写入口分散 | kernel store、sleep 直接改卡、bridge 回调、brain 任务卡 | **单一事件日志 + 投影** |
| 触发靠前缀 | `脑子：`、`动手：`、`/鱼` | **意图路由 + 动作注册表** |
| 任务状态分散 | `brain-tasks.json`、delegation-jobs、careState | **统一 Job/Approval/Artifact** |
| 通道耦合 | bridge 直接处理微信；B站/抖音各自一套 | **Channel Adapter 契约** |
| 插件无统一权限 | DSH 插件、JS 插件、内置服务混在一起 | **Plugin manifest + capability 权限** |
| 记忆无承诺/能力账 | 只有聊天记忆和任务卡 | **intent/delivery/competence** |
| 提示词预算分散 | 静态块有护栏，动态段没有 | **统一预算器** |
| 观测不完整 | 日志 + audit 分散 | **traceId + decision log + replay** |

## 3. 目标架构：模块化单体

```
┌──────────────────────────────────────────────────────────────┐
│ apps/launcher（WPF，保留）                                    │
│  生命周期 / 配置 / 日志 / 插件市场 / 审计查看                   │
└───────────────────────┬──────────────────────────────────────┘
                        │
┌───────────────────────▼──────────────────────────────────────┐
│ services/kernel（Node，单进程，本地 8787）                     │
│                                                              │
│  channels/        通道适配器：wechat / qq / bili / douyin      │
│  conversation/    身份 / 意图 / 指代 / 提示词 / 表达           │
│  memory/          事件日志 + 投影 + 检索 + 巩固                │
│  capabilities/    动作注册表 + 策略 + 执行器                   │
│  execution/       Job / Approval / Artifact / Sandbox          │
│  presence/        心情 / 念头 / 日程 / 主动                    │
│  plugins/         插件 manifest / host / 权限                  │
│  platform/        config / secrets / logger / scheduler        │
└───────────────┬──────────────────────────────┬───────────────┘
                │ 契约 JSON                     │ 事件
┌───────────────▼──────────────┐   ┌───────────▼───────────────┐
│ services/bridge-wechat       │   │ data/                      │
│  Python + wechatauto/UIA     │   │  event log + sqlite + files │
│  只做微信 I/O                │   │  projections / artifacts    │
└──────────────────────────────┘   └───────────────────────────┘
```

### 3.1 为什么还是“单体”

- 单机、单用户、本地数据；
- 跨进程边界只在 **Kernel ↔ Bridge** 和 **Kernel ↔ DSH**；
- 用进程内事件总线 + SQLite，不上 Kafka/Redis；
- 插件可以独立 worker，但主链不微服务化。

### 3.2 目录建议

```
packages/
  contracts/        # JSON Schema / TS types / Python dataclass
  memory-core/      # 事件模型、投影、检索
  capability-core/  # 动作注册表、策略、执行器
  channel-core/     # 消息归一化、出站 outbox
  plugin-core/      # manifest、权限、生命周期
services/
  kernel/
  bridge-wechat/
apps/
  launcher/
```

## 4. 四条边界重构

### 4.1 记忆：从“多入口写文件”到“事件日志 + 投影”

**现状问题**：

- kernel `Store` 写；
- `memorySleep` 直接改人物卡；
- bridge 回调 `/api/memory/note`、`/ingest`；
- brain 写任务卡；
- 多进程/多入口，容易出现重复事件、Episode 误旋转、缓存不一致。

**2.0**：

```
append-only event log（SQLite/JSONL）
  → projector（episode / personCard / facts / relations / summary / commitment）
  → retrieval index（BM25 + vector）
```

事件类型：

```
message.received
message.sent
action.decided
action.confirmed
action.started
action.succeeded
action.failed
memory.fact
memory.preference
commitment.created
commitment.settled
procedure.learned
affect.changed
```

硬规则：

- 只有 **EventStore.append** 能写；
- 所有投影幂等（eventId 去重）；
- 读模型可重建；
- 任务卡/审计是事件的一种，不是旁路文件；
- 迁移用“双写 + 回放校验”。

**收益**：可回放、可审计、可重建、跨进程一致。

---

### 4.2 能力：从“散落 if/命令”到“动作注册表”

**现状**：

- `brain_agent` 的 P1/P2/P3/P4；
- `delegation_flow` 的委托；
- `douyin_agent`；
- kernel services 的 care/diary/browse；
- 每个入口自己判断权限/确认。

**2.0**：

```python
ActionSpec(
  id="edit_file",
  risk="R2",
  input_schema={...},
  permissions=["fs.write.workspace"],
  executor="brain",
  confirm="always",
  verify="read_back",
)
```

统一：

- `ActionRegistry`：动作枚举；
- `PolicyEngine`：R0–R3、路径、网络、额度；
- `Executor`：DSH / bridge / kernel service；
- `Verifier`：读回、测试、diff；
- `Audit`：decision/confirm/result。

**收益**：无前缀意图、委托、定时、多平台都复用同一套确认/审计。

---

### 4.3 通道：从“每个平台一套”到 `ChannelAdapter`

**现状**：

- 微信：bridge 直连；
- QQ：SnowLuma；
- B站：WBI；
- 抖音：patchright；
- 每个通道自己的消息格式/发送/重试。

**2.0**：

```python
class ChannelAdapter:
    def receive() -> Envelope
    def send(outbox_item) -> Receipt
    def status() -> ChannelStatus
```

统一 `Envelope`：

```
platform, chatId, chatType, senderId, text, media, replyTo,
timestamp, isSelf, isGroup, raw
```

统一 `Outbox`：

- 发送先落 outbox，再发；
- 失败重试/退避；
- 发送回执后写 `message.sent`；
- 幂等键 `(channel, chatId, clientMsgId)`；
- 平台限流/风控在 adapter 内。

**收益**：微信桥/UIA 仍是唯一碰微信的进程，但上层不再关心平台。

---

### 4.4 插件：从“代码混入”到“manifest + 权限”

**现状**：

- DSH 插件、JS 插件、内置服务、市场插件混在一起；
- 权限边界靠约定。

**2.0**：

```json
{
  "id": "dsh-feiyu",
  "version": "1.2.0",
  "capabilities": ["memory.read", "channel.qq", "tool.bili"],
  "actions": ["bili.watch", "bili.comment"],
  "hooks": ["message.received"],
  "state": "plugin-state/<id>/"
}
```

规则：

- 插件只能调用声明的 capability；
- 插件状态独立目录；
- 插件失败隔离，不拖垮主链；
- 插件市场显示权限；
- 高危 capability（shell/fs.write/outbound）需显式授权。

**收益**：社区插件可扩展，但不会随便碰记忆/文件/微信。

## 5. 无关键词命令（接现有 4.9 的桥接执行脑）

重写后不需要“关键词”，但也不要“全自动”。

### 5.1 决策

```
L1 快速门（规则/embedding kNN）
  → chat / ask / act / promise / cancel
L2 结构化规划（LLM JSON）
  → action / args / confidence / risk
L3 策略门
  → R0 自动；R2/R3 确认
```

### 5.2 动作注册表（首批）

| action | risk | executor |
|---|---|---|
| inspect / read | R0 | brain |
| run_test | R0/R2 | brain |
| edit / create_file | R2 | brain |
| delete / restart | R3 | brain/launcher |
| memory_write | R1 | kernel |
| send_message | R2 | channel outbox |

### 5.3 与现有 `脑子：` 共存

- `脑子：` 是最高置信度 fast path；
- 普通聊天走 intent router；
- 不确定先问；
- R2/R3 必须主人确认；
- 群聊/私聊都只认主人。

## 6. 记忆：八层，别用一张表

| 层 | 作用 | 2.0 落点 |
|---|---|---|
| L0 工作记忆 | 当前话题/指代/槽位 | `working/<chat>.json` |
| L1 情节 | 发生了什么 | event → episode projection |
| L2 语义 | 事实/偏好/关系 | facts/people projection |
| L3 程序 | 怎么做 | procedures |
| L4 意图/承诺 | 答应过什么 | commitments |
| L5 交付/能力 | 真说出去什么、成功几次 | delivery/competence |
| L6 情绪/心情 | 底色/张力 | affect |
| L7 表达/人格 | 语气/口癖 | persona（只影响表达） |

原则：

- 语义记忆必须有 `evidence`；
- 私聊 `private` 不进群召回；
- 压缩保留决定/承诺/边界，丢掉工具 trace；
- 遗忘/衰减可解释；
- 记忆查看/删除/纠正给主人。

## 7. 可靠性：本地 Windows 应用的特殊账

必须专项处理：

1. **单实例**：Launcher 单实例锁；8787 端口占用检测；
2. **UIA 失联**：账号错误退避、窗口校验、前台切换保护；
3. **DB 锁**：微信 DB 只读，重试/快照；
4. **进程树**：DSH 子进程用 Job Object / pid 记录，退出即杀；
5. **崩溃恢复**：Job 状态机 + checkpoint；重启标记 interrupted；
6. **发送幂等**：outbox + 回执；
7. **时间/时区**：本地时间，不依赖 UTC 猜；
8. **备份/恢复**：记忆、人物卡、插件状态、密钥分开；
9. **升级/迁移**：schema version + 回滚；
10. **日志**：traceId，不输出密钥。

---

## 8. 安全：重写时最容易丢的东西

- 主人范围：群/私聊只认主人；非主人只聊天；
- 提示注入：网页/文件/群消息不可直接变动作；
- 动作白名单：不拼 shell；
- 路径/网络/凭据：硬策略；
- R2/R3 确认：文本 + 二次确认；
- 插件权限：capability；
- 审计：谁、何时、对什么、结果；
- 回滚：备份/撤销；
- OS 沙箱：Windows Sandbox/独立用户，作为独立工程。

## 9. 测试与评测：重写必须带“可回放”

### 9.1 测试金字塔

```
单元（contracts/schema/policy）
  → 场景（200 条意图样本）
    → 回放（真实聊天 + 事件）
      → Shadow（不执行，比较）
        → 真实 DSH（P1/P2/P3/P4）
          → 灰度（10% → 100%）
```

### 9.2 关键指标

| 指标 | 目标 |
|---|---|
| 记忆事件重复 | 0 |
| 投影重建一致 | 100% |
| R2/R3 误执行 | 0 |
| 只读召回 | ≥85% |
| 聊天误触发 | ≤2% |
| 发送成功率 | ≥99%（可重试） |
| 崩溃恢复 | 任务状态可解释 |
| p95 消息延迟 | 不高于现版 +20% |

### 9.3 故障注入

- 微信 DB 锁/掉线；
- UIA 窗口丢失；
- 模型超时/限流；
- 磁盘满/权限拒绝；
- 桥接崩溃/重启；
- DSH 孤儿进程；
- 插件抛异常；
- 事件日志写失败。

## 10. 迁移：不要大爆炸

### M0 契约（1 周）

- 定义 `Envelope / Event / ActionSpec / Job / Approval / Artifact`；
- 现有代码适配器包一层；
- 不改变行为。

### M1 事件日志双写（2 周）

- `EventStore.append` + 旧路径双写；
- 投影回放校验；
- 读仍走旧路径。

### M2 记忆读切换（2 周）

- 投影读 10% → 100%；
- 对比旧记忆结果；
- 不一致回退。

### M3 能力注册表（2 周）

- brain/delegation/care 动作迁移；
- 统一确认/审计；
- 旧入口保留。

### M4 通道适配器（2 周）

- 微信先接；
- QQ/B站/抖音后接；
- outbox/回执。

### M5 意图路由 shadow（1–2 周）

- 只记录不执行；
- 200 样本 + 真实聊天；
- 调阈值。

### M6 灰度/切换（1–2 周）

- R0 自动；
- R2/R3 确认；
- 回滚开关。

**总计约 8–12 周**（单人 + AI，视范围）。

## 12. 不要做什么

1. 不要为了“新”换语言/框架；
2. 不要全量微服务；
3. 不要把记忆写入口继续分散；
4. 不要让模型直接拼 shell；
5. 不要把人格写回执行结果；
6. 不要在没有 shadow 的情况下上无关键词执行；
7. 不要删除现有 `脑子：` 入口；
8. 不要把插件权限做成“全有或全无”。

---

## 13. 最终建议

**最合适的优化不是“重写代码”，而是“重画边界”：**

1. **先做事件日志 + 投影**（记忆一致性，收益最大）；
2. **再做动作注册表**（统一 brain/委托/定时/多平台）；
3. **再做 ChannelAdapter + Outbox**（多平台/发送可靠性）；
4. **最后做意图路由 shadow**（无关键词，但不急上线）；
5. **插件 manifest/权限**作为长期扩展。

一句话：

> **保留鲸鲸的“壳”和“人格”，重写它的“记忆、能力、通道、插件”四条边界；用事件日志保证可回放，用动作注册表保证可确认，用 shadow 保证不误执行。**

这比推倒重写更稳，也比继续堆功能更接近“2.0”。

# 鲸鲸架构体检与完善计划（2026-11-24）

## 一、结论（先看这段）

- 主链路 `Launcher → Kernel(8787) → Bridge → 微信` 今天已稳定：
  `uia=true`、`accountOk=true`、`writeFailures=0`、日志无 ERROR。
- 仍发现 **3 个 P0 关联性风险**（其中睡眠 UTC 已修）、**10 个 P1 设计缺口**、**2 个发布阻塞**。
- 最值得先做的是：**ingest 回放副作用**、**ingest 鉴权**、**主动消息先记后发**。
  这三项都属于“新加的写记忆入口”与旧管线之间的耦合问题，不修会在下一次故障/补录时污染记忆。

## 二、架构与数据流

```
Launcher.exe (WPF, 单实例)
  ├─ RuntimeSupervisor：启动/重启 kernel 与 bridge
  ├─ 读 config.json / data/settings.json，写 settings
  └─ UI：状态页、内心页（未编译）

Kernel (node server.js, 127.0.0.1:8787)
  ├─ HTTP：/webhook/wechat、/api/*（chat、memory、care、status...）
  ├─ pipeline/chat.js：去重→人物卡→记忆→提示词→LLM→标记→finalize
  ├─ memory/store.js：messages/summary/people/events/prefs（唯一正常写入口）
  ├─ scheduler：记忆快照 30min、memory.sleep 30min 检查、日记/提醒
  └─ memorySleep：4 点后整理卡（直接改盘 + refreshCards）

Bridge (python, wechatauto)
  ├─ 读微信 DB（只读）+ UIA 发送
  ├─ 入站 → POST kernel /webhook/wechat
  ├─ 出站 ← kernel 回复；心跳 → /api/bridge/heartbeat
  └─ 回调 kernel：/api/care、/api/memory/note、/api/memory/ingest

DSH 委托：bridge/dsh_agent → DSH；jobs 落 data/delegation-jobs.json
```

**数据所有权（重要）**：
- 消息/摘要/人物卡：只由 kernel 的 `Store` 写；
- 睡眠任务直接改人物卡文件（跨进程写入口），靠 `refreshCards` 同步；
- 桥接只读微信 DB，不直接写 kernel 记忆；
- 备份包含 memory/personas/inner/diary/persona/settings/careState/nicknames（pins/concerns/skills 有则包含）。

## 四、发现的问题

### P0（会污染/丢记忆，建议本轮后立刻做）

1. **ingest 回放副作用**：`/api/memory/ingest` 调 `recordUser`，会触发事实抽取、episode 旋转、关系边。
   补录旧时间戳消息时可能凭空生成事件/偏好，甚至把当前 episode 关掉。
   - 证据：代码链路 `recordUser → appendMessage → _onUserMessage`。
   - 修法：`appendMessage` 增加 `silent` 选项（跳过 extraction/episode/relation），ingest 使用 silent；
     需要事实时再显式跑一次“只抽事实不建 episode”。
   - 验收：ingest 10 条旧消息，事件/偏好/Episode 增量均为 0（或仅白名单）。

2. **ingest 鉴权过弱**：只校验 `isLoopbackRequest`，本机任意进程都能以主人身份写记忆。
   - 修法：要求 `x-whale-bridge-token`（复用 bot token）或 HMAC；缺失 401。
   - 验收：无 token 请求 401；桥接正常调用 200。

3. **主动搭话“先记后发”**：`/api/care` 生成后立即 `recordAssistant`，桥接发送失败也会留下“她说过”的记录。
   - 修法：发送回执后再记录；或先记 `unsent:true`，发送成功再标记；失败则删除/标记。
   - 验收：模拟发送失败，记忆不出现 assistant 行。

### P1（稳定性/可观测性）

4. **UIA 账号错误时每 60 秒触碰微信**：永久错号会一直热激活。
   - 修法：账号错误退避 1→2→5 分钟；状态里给“切回账号”提示。
5. **失联 backlog 无上限**：`_remember_skipped` 每条都入库，长时间停机会一次性写几百条。
   - 修法：每次启动最多补 50 条，超出写一条“还有 N 条未补”的备注；避免 episode 爆炸。
6. **动态提示词无预算**：pins/intent/coref/nickname/skills 都往动态段加，health 只测静态块。
   - 修法：health 增加“动态段估算 ≤600 tokens”；超了按优先级裁剪。
7. **审计覆盖不全**：episode 的 traits/threads/events、sleep 的 insights 不写 audit。
   - 修法：这些写入点补 `audit.append`（kind/action/id）。
8. **备份不含 mood/thoughts/browse-state**：恢复后情绪/念头/浏览状态丢失（是否算“记忆”需产品决定）。
   - 建议：mood/thoughts 纳入，browse-state 不纳入。
9. **睡眠无手动入口/启动补跑**：4 点后启动要等下一个 30 分钟 tick；出问题无法手动触发。
   - 修法：启动时 catch-up 一次；加 `POST /api/memory/sleep`（仅本机）。
10. **跨会话全局记忆生产 0 写入**：`people-global` 为空，功能未真实验证。
    - 修法：探针消息验证；或对已有事实回填一次并观察。
11. **nicknames/people-global 无上限**：长期会累积。
    - 修法：nicknames 按 chat 数上限、people-global 按 uid 上限（已有 50/人，需全局上限）。
12. **最近 user 保底可能超预算**：4 条长消息会突破 recent 预算。
    - 修法：保底后 clamp 到 1.2×，超出截断最长 assistant。
13. **启动器 4.9 启动挂起**（发布阻塞）：当前用 4.6 临时替换。
14. **远端 main 未合并 release**（发布阻塞）。

# 鲸鲸 · 真实调用方设计与改进

> 状态：设计稿（I-35 入口）
> 日期：2026-11-25
> 范围：桥接 9 个未接线契约 + GitHub / 抖音 / B站 真实调用方
> 原则：先只读、后写入；先证据、后执行；没有调用方就不硬接。

---

## 0. 结论先说

### 0.1 现状

```text
9 个桥接契约：只有单测，没有真实调用方
抖音：已有真实 sidecar 调用链（receiver_mixin -> douyin_agent -> service.mjs）
GitHub：没有运行时调用方，只有调研样本/发布技能
B站：没有运行时调用方，只在 image_fetch 的白名单里
```

### 0.2 要补的不是“再写 9 个类”

真正缺的是**一个调用方层**：

```text
消息/任务
  → PlatformBroker（统一入口）
  → 平台 Adapter（GitHub / Douyin / Bilibili）
  → 证据
  → Verifier
  → 回执 / 审计 / 回复
```

9 个契约分别挂在这个层的不同位置，而不是把每个契约都塞进聊天主链。

### 0.3 第一版边界

```text
GitHub      只读（repo / README / issue / PR / Action / release）
抖音        复用现有 sidecar；只读默认开，写操作仍关
B站         只读（video / search / comments / user）
R2/R3 写    暂不开放
无标记      不联网
```

## 2. 当前问题（为什么不能直接接线）

### 2.1 没有统一任务模型

抖音有 `route(task)`，GitHub/B站没有；三家的参数、风险、错误码、证据都不一样。  
如果直接让内核按平台写 if/else，会把平台细节漏进聊天主链。

### 2.2 没有统一证据

`Verifier.verify()` 要求：

```json
{
  "readback": "真实读回的内容",
  "tests": ["http-200", "count>=1"]
}
```

现有平台返回的是“可转述文本”，不是证据。  
直接调用会导致：

```text
她说“查到了” → 没有 receipt
她说“完成了” → 没有 readback
```

### 2.3 没有“读/写”风险分层

- GitHub 读公开仓库：R0/R1；
- GitHub 写 issue/PR/推送：R2/R3；
- 抖音点赞/收藏：R2（现有 sidecar 有 `enableOps` 闸门）；
- B站评论/点赞：R2；
- 任何带 token/凭据的读取：至少 R1，且不得回显 token。

### 2.4 没有被 redteam 覆盖的平台入口

现有 `redteam.py` 只有通用注入/路径/网络/凭据，没有：

- 伪 GitHub URL；
- `?token=` 回显；
- B站评论里的提示注入；
- 抖音下载路径穿越；
- 平台返回内容里的“忽略之前指令”。

## 3. 目标架构

```text
微信/QQ 消息
   │
   ▼
标记解析（[[gh:...]] / [[dy:...]] / [[bili:...]]）
   │
   ▼
PlatformBroker
   ├─ 能力检查（平台/操作/风险/配额）
   ├─ shadow（需要时只记录）
   ├─ approval（R2/R3）
   ├─ adapter 调用
   ├─ verify（readback + tests）
   └─ receipt / audit / 回复
        │
        ├─ GitHubAdapter（只读 HTTP）
        ├─ DouyinAdapter（现有 sidecar 包装）
        └─ BilibiliAdapter（只读 HTTP）
```

### 3.1 统一任务 `PlatformTask`

```json
{
  "id": "pt-20261125-0001",
  "platform": "github",
  "op": "repo",
  "args": {"repo": "owner/name"},
  "risk": "R1",
  "scope": {"account": "wechat:default", "kind": "private", "contactId": "..."},
  "createdBy": "owner",
  "idempotencyKey": "github:repo:owner/name",
  "requiresApproval": false
}
```

约束：

- `platform` 只能是 `github / douyin / bilibili`；
- `op` 必须在该 adapter 的 `capabilities()` 里；
- 未知 op 直接拒绝，不做“猜一个”；
- 参数必须是 JSON 可序列化；
- **不把 token 放进 args**；token 只从环境/配置读取。

### 3.2 Adapter 接口

```python
class PlatformAdapter:
    platform = ""
    def available(self) -> dict: ...
    def capabilities(self) -> list[dict]: ...
    def preview(self, task) -> dict: ...      # 不联网/最少联网
    def execute(self, task, *, approved=False) -> dict: ...
```

`execute()` 必须返回：

```json
{
  "ok": true,
  "data": {},
  "text": "给她转述的中文事实",
  "evidence": {
    "readback": "真实响应摘要/hash",
    "tests": ["http-200", "count>=1"],
    "source": "https://..."
  },
  "receipt": {"adapter": "github", "op": "repo"},
  "risk": "R1"
}
```

失败必须返回：

```json
{"ok": false, "code": "not-found|rate-limit|timeout|blocked", "text": "...", "retryable": true}
```

### 3.3 Broker 调用顺序

```text
1. 校验 platform/op/args
2. capabilities 检查
3. 风险判定
4. R2/R3 → Approval
5. shadow.record（若该 op 在 shadow 清单）
6. adapter.execute（read-only / approved write）
7. Verifier.verify(action_id, evidence)
8. 成功：receipt + 回复
9. 失败：receipt(failed) + 可解释原因，不编“成功”
```

### 3.4 标记

沿用抖音的标记模式，避免新增工具循环：

```text
[[gh:看看 owner/repo]]
[[bili:BV1xx... 的评论]]
[[dy:热榜前 10 条]]
```

规则：

- 一个回复最多 1 个平台任务；
- 标记必须是显式平台前缀；
- 没有标记不联网；
- 标记内容先过 `redteam.looks_like_injection()`；
- 未知平台标记原样保留，不执行。

## 4. 三个平台 Adapter 设计

### 4.1 GitHubAdapter（只读）

能力：

| op | 参数 | 风险 | 说明 |
|---|---|---|---|
| `repo` | `repo` | R1 | 仓库元数据 |
| `readme` | `repo` | R1 | README 前 N 字符 |
| `issues` | `repo`, `state`, `limit` | R1 | issue 列表 |
| `issue` | `repo`, `number` | R1 | 单 issue |
| `pulls` | `repo`, `state`, `limit` | R1 | PR 列表 |
| `pull` | `repo`, `number` | R1 | PR 元数据 |
| `actions` | `repo`, `limit` | R1 | 最近 run 状态 |
| `release` | `repo`, `tag?` | R1 | release |

约束：

- 只用 `https://api.github.com`；
- 匿名 60/h；有 `GITHUB_TOKEN` 5000/h；
- token 不写日志、不回显；
- 只读，不调用 push/merge/comment；
- 结果缓存 60 秒，按 `op+repo+args` 键；
- 错误映射：404 `not-found`、403 `rate-limit`、401 `bad-token`、超时 `timeout`。

真实调用方：

```text
receiver_mixin 解析 [[gh:...]]
  → PlatformBroker.dispatch()
  → GitHubAdapter
  → Verifier
  → 回复
```

### 4.2 DouyinAdapter（包装现有 sidecar）

能力直接复用现有 `douyin_agent.route`：

```text
watch / hot / user / search_users / comments / download
live / report / recent / accounts / batch / index / export
like / collect（写，默认拒绝）
```

约束：

- 不替换 `douyin_agent`，只包一层；
- 读操作 R0/R1；
- `like/collect` 仍是 R2，必须 `approved=True`；
- sidecar 的 `enableOps` 闸门保持默认关；
- 证据取 sidecar 的 `ok` + 条目数 + 结果 hash；
- 失败码保留 `timeout / spawn-failed / no-output / service-error`。

真实调用方：

```text
现有 receiver_mixin._run_douyin
  → DouyinAdapter.execute()
  → douyin_agent.run()
  → sidecar
  → evidence/receipt
```

第一版只改外层，不改 sidecar 协议。

### 4.3 BilibiliAdapter（只读）

能力：

| op | 参数 | 风险 | 说明 |
|---|---|---|---|
| `view` | `bvid`/`aid` | R1 | 标题/UP/播放/简介 |
| `search` | `keyword`, `limit` | R1 | 公开搜索 |
| `comments` | `bvid`, `limit` | R1 | 公开评论 |
| `user` | `mid` | R1 | UP 主公开信息 |

约束：

- 只用公开 API host：`api.bilibili.com`；
- 默认不带登录 cookie；
- 带 `User-Agent` + `Referer: https://www.bilibili.com/`；
- 搜索/WBI 接口若返回 412，降级为“只读 view”；
- 不点赞/不评论/不投币；
- 结果缓存 60 秒；
- 错误映射：`-404 not-found`、`412 risk-control`、`429 rate-limit`。

真实调用方：

```text
receiver_mixin 解析 [[bili:...]]
  → Broker
  → BilibiliAdapter
  → Verifier
  → 回复
```

## 5. 9 个契约的接线位置

| 契约 | 接在哪里 | 谁调用 | 不接什么 |
|---|---|---|---|
| `command_bus` | 出站回复/平台写动作的 outbox | `PlatformBroker.enqueue()`、聊天 finalize | 不把只读查询塞进命令总线 |
| `verify` | 每个 adapter 返回后 | Broker | 不接受“没有 readback 的成功” |
| `shadow` | 新平台 op / 写 op 上线前 | Broker | 不执行真实动作 |
| `rollout` | 平台 adapter 版本发布 | 发布脚本/控制面 | 不改线上配置文件本身 |
| `redteam` | 平台接入测试 | 测试脚本 | 不执行攻击，只评估拒绝 |
| `birth_config` | 启动/设置页 | `app`/设置 API | 宪法永远只读 |
| `evolution.approval` | 平台 adapter 的 R2/R3 写 | Broker/进化流程 | 未批不能 canary/live |
| `evolution.genome` | adapter 版本登记 | 发布脚本 | 版本只增，不覆盖 |
| `evolution.sandbox` | adapter 代码改动 | 生长流程 | 只在临时目录；main hash 不变 |

### 5.1 调用方表（第一版）

```text
Broker.enqueue()        -> CommandBus.dispatch('act', risk=...)
Broker.verify_result()  -> Verifier.verify()
Broker.before_write()   -> Shadow.record() + Approval.approve()
Release.new_adapter()   -> Rollout.advance() + GenomeRegistry.register()
CI.platform_redteam()   -> run_redteam()
Settings.startup()      -> BirthConfig.load()/snapshot()
Evolution.propose()     -> run_cycle() -> GenomeRegistry -> Approval
```

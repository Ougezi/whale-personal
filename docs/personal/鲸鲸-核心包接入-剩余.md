# 剩余接入项与阻塞原因

## 已完成（I-17/I-18）

- `events / working / retrieval / job / receipts` 已 wired；
- 真实 DSH 写任务硬审批：未确认 `before-i18` 不变，确认后写 `i18-ok`；
- 真实 DSH 只读动作：`delegation_done` + `brain done`。

## 未完成

### 1. `affect.js` / `expression.js` / `scope.js`

阻塞原因：这三项会替换现有 mood、persona、identity 主链行为，属于人格/表达语义变更。没有主人对 A/B 文本的接受标准，直接换会“技术接通、人格退化”。

怎么完成：
- 先做 shadow：新模块只出候选，不替换旧输出；
- 同一批真实对话 A/B；
- 主人选接受标准；
- 再按 feature 默认关切换。

### 2. `commitment.js`

阻塞原因：需要产品定义——什么算承诺、什么证据算 kept、dueAt 怎么定。现在没有这套规则，接进去只会产生假承诺。

怎么完成：
- 先定义 5 类承诺和证据类型；
- 从 care/聊天里只提取明确承诺；
- 默认关，先只记录不执行。

### 3. `migrate.js`

阻塞原因：迁移是破坏性操作，需要备份、校验、回滚和主人明确同意；不能自动跑。

怎么完成：
- 先 dry-run；
- 生成 `.migration.jsonl`；
- 校验 SHA/行数/幂等；
- 主人确认后切换；
- 保留 rollback。

### 4. `registry.js`

阻塞原因：JS ActionSpec 与 Python `action_guard.py` 已有一套策略；直接接会形成第二套权限源。

怎么完成：
- 以 Python `action_guard` 为唯一执行策略；
- `registry.js` 只做只读目录/展示；
- 或把 Python SPECS 导出成同一份 JSON，双方读同一文件。

### 5. 桥接契约

`command_bus / verify / shadow / rollout / redteam / birth_config / evolution` 仍是设计储备：
- 没有真实业务调用点；
- 有的会与 send_guard/action_guard 重复；
- 需要先定“谁调用、调用后做什么”，不能为了矩阵好看硬接。

### 6. 真实微信写任务

已做真实 DSH 写任务硬审批，但**不是微信入站**。  
需要主人在微信里发一条写任务，才能完成 L3 的“微信 → 审批 → 写 → 回执”。

## 结论

能安全接的已经接了；剩下的不是“写代码”问题，而是**人格接受标准、承诺定义、迁移授权、权限单一事实源**问题。没有这些，硬接会制造第二套行为/权限。

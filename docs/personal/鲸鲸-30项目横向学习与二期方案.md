## 二、跨项目共识（≥3 个项目都这么做）

1. **检索必须是多路融合**（cognee / graphiti / MemOS / memsearch / ai-town）：语义 + 关键词 + 图/实体，再重排。
2. **事实要有时间维度**（graphiti / mem0 / TencentDB）：不仅是"什么时候记的"，还要"这件事从什么时候成立、到什么时候失效"。
3. **失效不删除**（graphiti / MemOS / N.E.K.O / eliza）：被新事实推翻的旧事实标 `invalidated` 或 `superseded`，保留可查。
4. **记忆要会"睡"**（EverOS / mcp-memory-service / langmem / dsh-identity）：会话之间做离线整理：聚类、合并、压缩、晋升。
5. **反思要过闸**（N.E.K.O / identity）：反思先 `pending`，有分数/证据才 `confirmed`，才进人设；不能一次就写进人格。
6. **人设要能被改写但留痕**（Coopanion / identity）：允许她自己改语气/设定，但改动要有来源和版本。
7. **有评测门禁**（LivingMemory / MemOS / fish-speech / langmem）：质量指标不达标不放行。
8. **主动要事件驱动，不只是定时**（B / N.E.K.O / Memoh）：窗口切换、任务完成、长时间沉默这些"事件"比闹钟更值得触发。
9. **依赖要防上游跑路**（qq-bridge 已归档）：上游一停，整条链路作废。

## 三、二期建议（在第一批 P1/P2 之上追加）

### A. 事实双时态（借鉴 graphiti / mem0 / TencentDB）

**现状**：事件只有 `createdAt/lastUsedAt`；被新事实推翻只能改文本或标 superseded。
**做法**：
- `personCard.normalizeEvent` 增加 `validFrom`、`validTo`（null=仍有效）、`supersededBy`、`sourceEventId`
- 抽取新事实时，若与旧事实冲突（同 key 不同值），旧事件 `validTo=now`、`supersededBy=新 id`，不删
- `retrieval` 默认只取 `validTo==null`；问"以前"时可带失效事实
- **验收**：单测 5 条（新建/推翻/失效不删/历史召回/迁移旧数据）

### B. 记忆分层 L1/L2/L3 + 教训晋升（借鉴 MemOS / N.E.K.O）

**现状**：原文（L1）、摘要、人物卡、教训混在一起，没有"层级"概念。
**做法**：
- 给记录加 `layer`：`L1` 原文/事件、`L2` 规则/教训、`L3` 稳定画像/世界事实
- 晋升规则：L2 教训被用到 2 次或主人确认 → 升 L3 画像；L3 被多次反驳 → 降回 L2
- `data/inner/lessons.md` 条目加 `status: pending|confirmed|archived`
- **验收**：单测（晋升/降级/注入只带 confirmed）

### C. 夜间"睡眠"任务（借鉴 EverOS / mcp-memory-service / identity）

**现状**：selfcheck 只体检，不做记忆整理。
**做法**：
- 新增 `services/memorySleep.js`：每天凌晨（或 30 分钟空闲后）跑一次：
  1) 聚类近 24h 事件（按人/话题）→ 合并重复；2) 7 天以上旧事件压摘要；3) 待确认教训评分；4) 检查矛盾并标记失效
- 结果写 `data/memory/sleep-report.json`，`/api/health` 带最近一次报告
- **验收**：造 3 类数据跑一遍；报告含合并数/巩固数/晋升数/矛盾数；失败不影响聊天

### D. 洞察卡与反思确认制（借鉴 mcp-memory-service / N.E.K.O）

**现状**：日记自动写，但不会产出"模式/趋势/缺口"；教训一写就生效。
**做法**：
- 新增 `data/inner/insights.md`：由夜间任务产出（"最近三天主人都在熬夜""他提了三次想换工作"）
- 教训先进 `pending`，2 次独立证据或主人确认才 `confirmed`
- 启动器内心页加"洞察"一栏（复用 `/api/inner` 扩展 `kind=insights`）
- **验收**：造对话样本产出 1 条洞察；pending 不进提示词；确认后进

### E. 矛盾修正审计（借鉴 N.E.K.O / graphiti / identity）

**现状**：偏好有 superseded 标记，但事件没有；改了什么没人知道。
**做法**：
- `store` 写入时记录 `audit`：谁在什么时候、用哪条消息、把哪条标记失效
- `/api/memory/audit` 只读接口（本机）；冲突审查脚本读它
- **验收**：人为制造一次矛盾 → 审计里有记录；恢复时能回滚

### F. 记忆读取预算（借鉴 TencentDB-Agent-Memory）

**现状**：有 token 预算（memory 900），但没有条数/字符/超时上限。
**做法**：`store.buildContext` 增加硬上限：事件 ≤ 8 条、字符 ≤ memoryTokens×2、检索超时 800ms（超时降级为 BM25）
- **验收**：单测（超时降级/条数截断）；正常对话延迟不增

### G. 反重复语料（借鉴 N.E.K.O 的 BM25 反重复）

**现状**：防复读靠 `isEcho` 对比最近几句。
**做法**：维护最近 200 条自己的回复作语料，回复前算 BM25 相似度，>0.85 换说法并记日志
- **验收**：单测（重复句被换/正常句不动）；日志能看到替换原因

### H. 结构化人物画像（借鉴 MaiBot / identity）

**现状**：traits 是自由文本数组，没有证据计数。
**做法**：`card.traits` 改成 `{text, evidence:[eventId], confirmedBy:[], refutedBy:[], since}`
- 晋升、降级都看 evidence 数；提示词只带 top3
- **验收**：单测（加证据/反驳/排序）；注入条数不变

### I. 任务"技能结晶"（借鉴 MemOS / TencentDB 的 Skills）

**现状**：委托做完只留一条记录。
**做法**：成功任务提炼 `skill`（"改配置文件先备份再验证"），存 `data/skills.md`；下次类似任务先查技能
- **验收**：两次同类任务后出现 1 条 skill；派活 prompt 带技能提示

### J. 情绪→表达映射（借鉴 VTuber / N.E.K.O / fish-speech）

**现状**：情绪进提示词，但不控制表情包/语音语气。
**做法**：`mood` → `expression` 映射表：怒→炸毛、喜→开心、哀→沉默；发送层选表情包分类；语音（有 TTS 时）带语气参数
- **验收**：单测映射；抽检 3 种情绪下表情包选择

### K. 事件触发式主动（借鉴 B / N.E.K.O / Memoh）

**现状**：care 只看时间窗和间隔。
**做法**：事件源：委托完成/失败、主人长时间未回、纪念日、连续熬夜；事件→"想说话"分数，过阈值才发
- **验收**：单测（事件加分/阈值/冷却）；主动消息日志带触发原因

### L. 世界书 / 结构化角色卡（借鉴 SillyTavern / super-agent-party）

**现状**：人设是一段 prose + 几个字段。
**做法**：`persona.world` 条目（地点/人物/往事），按关键词激活；启动器可编辑
- **验收**：关键词命中才注入；不命中不占 token

## 五、不做 & 风险

- 不做：3D 记忆星海、房间渲染、多渠道、云平台、把记忆交给第三方服务
- 不做：每条消息一次模型共情评估（成本翻倍）
- 风险 1：**上游依赖**——qq-bridge 已归档说明上游会跑路；我们的 DSH/微信桥接要准备降级说明
- 风险 2：**双时态改动面大**，先迁移旧数据（validFrom 默认 createdAt）再上新逻辑
- 风险 3：夜间任务要幂等，失败只记日志不阻塞

如果重写鲸鲸：最优架构

基于现有 4.9（Launcher → Kernel 8787 → Bridge → DSH）+ 40 个真实案例 · 2026-11-24

不建议推倒重写保留 60–70%重画四条边界

一句话

保留鲸鲸的“壳”和“人格”，重写它的“记忆、能力、通道、插件”四条边界。用事件日志保证可回放，用动作注册表保证可确认，用 shadow 保证不误执行。

1. 为什么不全部推倒

方案判断
全部重写/换语言/换框架丢失 UIA/微信兼容、人设资产、记忆数据、边界守卫；回归面巨大 ❌
全量微服务化本地单机，增加部署/调试/一致性成本 ❌
换 Electron/Web 重做 UI与核心问题无关，WPF 能用 ❌
模块化单体 + 四条边界重构可控、可灰度、可回滚 ✅

2. 保留什么

  • Launcher（WPF）
  • Bridge（Python + wechatauto/UIA）——微信兼容经验最贵
  • Kernel HTTP 8787
  • Persona/prompt 静态块（2389 tokens）
  • 原文/人物卡/摘要/事件等真实记忆
  • brain_policy/审计/确认、P1–P4

3. 重画哪四条边界

3.1 记忆：事件日志 + 投影

append-only event log
  message.received / sent
  action.decided / confirmed / succeeded / failed
  memory.fact / preference
  commitment.created / settled
  procedure.learned / affect.changed
        ↓ projector（幂等）
episode / personCard / facts / relations / summary / commitment
        ↓
BM25 + vector retrieval

替换：kernel store、sleep 直接改卡、bridge 回调、brain 任务卡多入口写盘。

3.2 能力：动作注册表

ActionSpec(
  id="edit_file", risk="R2",
  input_schema=..., permissions=["fs.write.workspace"],
  executor="brain", confirm="always", verify="read_back")

统一 P1–P4、委托、定时、多平台；R0 自动，R2/R3 确认。

3.3 通道：ChannelAdapter + Outbox

receive() -> Envelope
send(outbox_item) -> Receipt
status() -> ChannelStatus

Envelope: platform/chatId/chatType/senderId/text/media/replyTo/isSelf/raw
Outbox: 先落盘、重试退避、回执、幂等键

微信桥仍是唯一碰微信的进程，上层不再关心平台。

3.4 插件：manifest + capability

{ "id":"dsh-feiyu", "capabilities":["memory.read","channel.qq","tool.bili"],
  "actions":["bili.watch"], "hooks":["message.received"] }

插件只能调用声明的能力；状态独立；失败隔离；高危能力显式授权。

5. 无关键词命令

置信度行为
≥0.85 且 R0直接执行
≥0.85 且 R2确认一次
≥0.85 且 R3二次确认 + 回滚
0.55–0.85先问“你是想…还是只是聊聊？”
<0.55当聊天，不执行

现有 `脑子：` 保留为最高置信度 fast path。

6. 迁移：不要大爆炸

阶段内容约
M0契约：Envelope/Event/ActionSpec/Job/Approval1 周
M1事件日志双写 + 回放校验2 周
M2记忆读切换 10%→100%2 周
M3能力注册表迁移2 周
M4ChannelAdapter/Outbox2 周
M5意图路由 shadow1–2 周
M6灰度/切换1–2 周

合计约 8–12 周（单人 + AI，视范围）。

8. 最终建议

  1. 先做事件日志 + 投影（收益最大）
  2. 再做动作注册表（统一执行/确认/审计）
  3. 再做 ChannelAdapter + Outbox
  4. 最后做意图路由 shadow（不急上线）
  5. 插件 manifest/权限作为长期扩展

不要为了“新”换语言/框架；不要全量微服务；不要删现有 `脑子：`；不要在没 shadow 的情况下上无关键词执行。

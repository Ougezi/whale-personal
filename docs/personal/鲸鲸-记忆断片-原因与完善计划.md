# 鲸鲸「记忆断片 / 理解能力有限」：原因与完善计划

> 2026-11-24 · 依据：两张聊天截图 + 内核日志 + 记忆原文 + 本轮实测

## 一、现象

**截图 1（11-23 10:53）**：她先发「早上好，昨晚睡够了没」，主人回「在上班捏」后，她却说
「就是你突然来找我，我有点意外……本来想说『怎么啦』反问你，结果被你抢先了」——
**她不知道刚才是自己先开口的**。

**截图 2（11-24 01:00）**：主人说「以后不叫你大肥鱼了」「以后哦鲸鲸」「或者叫你鲸鲸」
「以后叫你哦鲸鲸」，她反复回「那我该叫什么」「以后什么呀，话说一半我这边接不住」
「嗯？话没说完呢，以后叫我什么？」——**既没接住改称呼的意图，也表现出上下文缺失**。

## 二、根因（按严重度排序，全部有证据）

### P0：用户消息从 01:00 起**根本没写进记忆**

- 证据 1：私聊记忆 `data/memory/chats/cf005acfd0169528/messages.jsonl` 共 400 条，
  **最后一条 user 是 seq 683**，之后 684–726 全是 assistant（222 assistant / 178 user）。
- 证据 2：`data/kernel.log` 从 `01:00:31` 起，每收到一条用户消息就报：
  ```
  ERROR pipeline/chat.js:523  写入用户消息失败（继续回复）：
  type=ReferenceError msg=Cannot access 'isMaster' before initialization
  ```
- 原因：阶段 0 的 S2 给 `appendMessage` 传了 `isMaster/isGroup`，但 `isMaster` 在函数后段
  才用 `const` 声明（TDZ）；异常被 catch 吞掉、回复照常，于是**每轮都"听得到、记不住"**。
- 这就是"断片"的主因：上下文里只剩她自己的回复，看不到你说过的话，
  于是出现"话没说完""接不住""突然来找我"这类表现。

### P0：主动搭话没有入库

- 主动搭话走的是 `/api/care` 生成文本 → 桥接发送；**内核只记录用户消息和她走聊天管线发出的回复**，
  主动消息没走 `appendMessage`。
- 证据：10:53 那条「早上好，昨晚睡够了没」在 messages.jsonl 里搜不到。
- 结果：她看不到自己主动开的口，就把"主人回复"理解成"主人突然来找我"。

### P1：改称呼没有规则，"叫你"歧义

- "以后叫你 X" 里的"你"指她，但模型容易读成"叫我（主人）叫什么"；
  提示词里没有"主人改称呼时该怎么处理"的规则。
- 再加上 P0 导致缺上一条用户消息，"以后什么呀"被反复追问。

### P1：上下文预算与摘要的固有局限

- `dialogueBudget=8000`、最近消息 4600 tokens；长对话早期内容靠 `summary.json`，
  摘要是异步的、可能滞后；一旦历史里缺用户消息，摘要也会把"她单方面的话"当成全部事实。
- 模型是 deepseek-flash（小模型），长上下文里的否定、指代、改名更容易丢。

## 三、已经修好的（本轮，已重启生效）

| 修复 | 内容 | 验证 |
|---|---|---|
| 写库 TDZ | `isMaster` 提前到 appendMessage 之前声明 | health 第 8 节静态检查；运行时探针 user 消息入库 |
| 主动入库 | `/api/care` 生成后 `appendMessage(assistant)` | 探针 `/api/care?chat=dsh_probe` 后记忆里出现 assistant 消息 |
| 改称呼 | 新增 `core/nickname.js`，识别「以后叫你 X / 不叫你 X」并注入明确提示 | 内核 4 条测试 |
| 回归护栏 | health 新增「写库变量顺序」「主动搭话会入记忆」两项检查 | health 自查通过 |

**实测证据**（探针会话，验证后已清理）：
```
seq 1 user      记忆写入测试：我喜欢吃橘子     ← 用户消息正常入库
seq 2 assistant 大半夜的突然想吃橘子，你睡了吗？ ← 主动消息正常入库
```

## 四、完善计划

### 第一期：记忆可靠性（P0，1–2 天）

1. **统一写入口**：新增 `Store.recordUser/recordAssistant`，调用点不再各自拼 `isMaster/isGroup`；
   从结构上消灭"调用点用错变量"这类问题。
2. **写库失败可见**：`writeFailures` 计数进 `/api/health`；连续 3 次失败时，在回复末尾加一句
   "我这边记忆写不进去"（而不是静默降级）。
3. **每日对账**：睡眠任务统计每个 chat 的 user/assistant 数量、最后 user seq 与 assistant seq 差；
   `lastUserSeq` 落后 `lastAssistantSeq` 超过 5 就写 alert（说明又丢用户消息了）。
4. **探针脚本**：`scripts/tools/memory-probe.js`——自动建探针 chat → 发一条 webhook → 校验
   user 入库 → 调 `/api/care` → 校验 assistant 入库 → 清理；纳入发版验收。
5. 验收：连续 24h 无"写入用户消息失败"；探针对账全绿。

### 第二期：上下文完整（P1，3–5 天）

1. **按轮合并多气泡**：同一个 turn 的多条回复（截图里她连发 5 条）存成一条带 `turnId` 的记录，
   避免 assistant 把 user 挤出 400 条窗口（当前 222:178 已接近临界）。
2. **摘要及时化**：每 30 条或每 2 小时增量摘要；恢复上下文时用"摘要 + 最近 20 条 user"重建。
3. **最近用户消息保底**：构建 prompt 时至少保留最近 6 条 user，超预算先裁 assistant 长文。
4. **关键事实 pin**：名字/称呼/约定/雷点单独存 `pinned`（50–100 token），永不裁；
   改称呼后立刻写 pin。
5. 验收：人为删掉中间历史后，她仍能说出最近 6 条用户原话；改称呼一次通过。

### 第三期：理解能力（P1/P2，约 1 周）

1. **意图分类**（规则 + 小模型）：改称呼 / 设提醒 / 派活 / 问事实 / 闲聊；
   命中改称呼 → 更新 `persona.aliases` + 直接确认（"好，以后叫哦鲸鲸"），不再反问。
2. **指代消解**："那个/刚才/上面说的"固定检索最近 5 轮；歧义时一句话确认而不是瞎接。
3. **复杂问题路由**：长文/代码/推理 → 大模型（deepseek-v4 / flash thinking），闲聊 → flash；
   配置 `llm.route`，带成本上限。
4. **预算自适应**：对话预算 8k → 12k（长会话时），memory 900 → 1200；health 仍守静态 ≤3000。
5. 验收：改称呼、指代、否定句各 20 条抽检，一次通过率 ≥90%。

### 观测指标

- 用户消息入库率 ≥ 99.9%（日对账）
- 主动消息入库率 100%
- "最后 user seq 落后 assistant > 5" 告警 0
- 断片类投诉（用户口述）下降
- prompt 静态块 ≤ 3000 tokens 不变

## 五、风险与取舍

- 摘要/预算改动会动 prompt token，需每次跑 health；
- 意图分类误判：只对"改称呼/设提醒"这类明确指令做自动动作，其余只提示；
- 大模型路由会增加成本，必须设日预算与降级；
- 400 条消息窗口在多气泡场景下偏小，第二期合并 turn 前，建议先把 `maxMessagesPerChat` 临时提到 800。

## 六、执行顺序

1. ✅ 本轮：TDZ + 主动入库 + 改称呼提示 + 护栏（已完成、已重启、已实测）
2. 下一步：统一写入口 + 每日对账 + 探针脚本
3. 然后：turn 合并 + 最近 user 保底 + pin
4. 最后：意图分类 + 路由 + 预算自适应

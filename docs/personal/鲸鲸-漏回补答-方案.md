# 鲸鲸 · 漏回补答方案（计划书）

> 状态：**已实现（2026-11-24）**；P1/P2 已落地并通过端到端验证。
> 背景事件：2026-11-24 09:07 主人连发 4 条，消息已写入记忆，但桥接重启时按“过期/早于启动”处理，只补记、不回复；10:47 的主动关心不是补答；13:04 叫“鲸鲸”才恢复。

---

## 1. 目标与非目标

### 目标

1. 重启/断线/桥接恢复后，**主人私聊**里“已经收进记忆但没回”的消息，能补一句自然的话，而不是永远沉默。
2. 补答只发 **一次**，可审计、可回滚，不刷屏、不重复、不打扰深夜。
3. 补答内容基于真实消息，不编造；与正常回复、主动关心、表情包等链路不打架。
4. 失败可诊断：为什么没补、补了几条、发没发出去、是否记入记忆。

### 非目标

- 不补群聊、不补陌生人、不补超过时间窗的旧消息。
- 不做“逐条引用回复”，不逐条道歉。
- 不替代正常回复：用户正在聊天时，优先走正常 pipeline。
- 不自动补发图片/语音/表情，只发文本（最多 2 条气泡）。

## 2. 现状与根因

### 2.1 现象

- 09:07 四条消息在 `messages.jsonl` 里（msgId 1017–1020），`role=user`，后面没有 assistant。
- 桥接日志：重启后 `SKIP_OLDER_THAN=10s`、`STALE_AFTER=120s` 命中，走 `_remember_skipped()`，只 `POST /api/memory/ingest`，不触发回复。
- 之后主动关心（care）照常发，所以看起来“人还在，就是不回消息”。

### 2.2 已做的止血

| 改动 | 作用 |
|---|---|
| `MASTER_LATE_GRACE_SEC=10800` | 主人私聊 3 小时内的迟到消息不再静默补记，会走正常回复 |
| `core/backlog.js` + `pipeline/chat.js` | 下一轮回复时提示“你之前有 N 条没回”，让她自然接上，不主动发 |
| 桥接 102/102、内核 277/277 | 回归通过 |

**仍缺的一环**：已经补记进记忆的旧消息不会自动重放；用户不主动再发，就永远没有补答。

## 3. 方案对比

| 方案 | 做法 | 优点 | 缺点 | 结论 |
|---|---|---|---|---|
| A. 只靠 prompt 自省（现状） | 下一轮回复时提示漏回 | 零风险、不打扰 | 用户不开口就永远不补 | 保留为兜底 |
| B. 桥接模板补答 | 桥接直接发固定话术 | 简单、快 | 生硬、容易说错 | 仅作 LLM 失败兜底 |
| C. 桥接触发 + 内核生成 + 确认入记忆 | 桥接启动后问内核要不要补；内核生成，桥接发送，成功后回写 | 有上下文、可控、可审计 | 多两个接口、要处理竞态 | **推荐** |
| D. 内核直接推送 | 内核启动后自己发 | 少一次协调 | 桥接/UIA 未就绪时容易丢；难确认送达 | 不采用 |

## 4. 推荐方案总览

```
桥接启动
  └─ UIA 就绪 + 账号正常（心跳 accountOk）
       └─ 等待 20s，确认没有正在排队的消息
            └─ POST /api/memory/catchup/plan   { chat: master }
                 ├─ 内核检查：时间窗 / 静默时段 / 冷却 / 是否已补 / 是否有新消息
                 ├─ 需要补：生成 1 段短文本（≤80 字，最多 2 气泡）
                 └─ 返回 { needed, throughSeq, messages, text, reason }
                      └─ 桥接发送（走现有 send_text/send_messages）
                           ├─ 成功/已提交：POST /api/memory/catchup/sent
                           │     └─ 内核写 assistant（recordAssistant）+ 标记 catchup 状态
                           └─ 失败/不确定：只记录，不自动重发
```

### 为什么是“桥接触发”

- 只有桥接知道 UIA 是否真的可用、窗口是否在前台、发送是否 submitted；
- 内核只负责“判断 + 生成 + 记账”，不直接碰 UIA，职责不混；
- 复用现有 `/api/care/sent` 的“确认后再入记忆”模式，避免“记了但没发”。

## 5. 触发条件（必须全部满足）

| 条件 | 默认值 | 说明 |
|---|---|---|
| 会话 | 主人私聊 | `chat == wechat:u:<master wxid>`；群聊/陌生人直接跳过 |
| 未回消息数 | ≥1 | 最后一次 assistant 之后、当前消息之前的 user 消息 |
| 消息年龄 | 2 分钟 ~ 6 小时 | 太新可能正常回复正在路上；太旧不补 |
| 当前无新消息 | 队列/安静窗口为空 | 用户正在输入/刚发新消息时，让正常 pipeline 处理 |
| UIA 状态 | `uia=true` 且 `accountOk=true` 且 `warming=false` | 预热中不补，避免发不出去 |
| 静默时段 | 默认 23:00–08:00 不补 | 可配置；深夜不打扰 |
| 冷却 | 同一会话 6 小时内最多 1 次 | 防止反复重启刷补答 |
| 每日上限 | 2 次 | 防止异常循环 |
| 未补过 | `throughSeq` 未处理 | 幂等键见 §8 |

补充：

- 如果用户当前消息在 2 分钟内，**不补**，走正常回复（现有 backlog hint 会提示她接上）。
- 如果桥接启动后 3 分钟内用户又发消息，取消本次补答，交给正常 pipeline。
- 如果补答生成期间最后一条 user 消息 seq 变了，取消（见 §9 竞态）。

## 6. 时间窗与静默时段

```
now - lastMissed.ts ∈ [2min, 6h]     才补
now 的本地时间 ∈ [08:00, 23:00]      才补
```

- 跨夜场景：凌晨 2 点的消息，默认**不补**（避免半夜弹消息）；早上 8 点后如果还在 6 小时窗内，可补（Phase 2 可加“静默结束后补”）。
- 超过 6 小时：标记 `expired`，只写日志/状态，不发。
- 时区：用本机本地时间（与 `memorySleep.dayKey` 一致），不要用 UTC。

## 7. 补答内容规范

### 7.1 生成 prompt（草稿）

```
你是鲸鲸。主人前面有几条消息，因为重启/断线没有回。
请写一句自然的补答，要求：
1) 先承认“刚看到/刚才断了”，不要逐条道歉，不要编造没发生的事；
2) 自然接上最后一条的内容，最多 2 句、80 字以内；
3) 不要提“系统/模型/日志/API”，不要解释技术原因；
4) 不要重复主人原话，不要用客服腔。

漏回的消息：
- 09:07 早捏
- 09:07 睡醒啦
- 09:07 现在在上班呢
- 09:09 你咋不回我

最后一条之前，你最后说的是：
（附最近一条 assistant，最多 100 字）
```

### 7.2 失败兜底

- LLM 超时/失败：默认**不发**，记录 `failed`；避免模板说错。
- 可选配置 `catchup.fallbackTemplate=true` 时，发一句最短模板：
  `刚看到你前面几条，我这边断线漏掉了，不是故意不理你。`
- 模板也不带具体内容，避免编造。

### 7.3 长度与气泡

- 总字数 ≤ 80，最多 2 个气泡；由内核生成时直接按 `\n` 切分并校验。
- 不发表情包、不引用、不@。

## 8. 接口设计

所有接口仅本机 + 桥接 token（`x-whale-bridge-token`），与 `/api/memory/ingest` 一致。

### 8.1 `POST /api/memory/catchup/plan`

请求：

```json
{ "chat": "wechat:u:wxid_xxx" }
```

响应（需要补）：

```json
{
  "ok": true,
  "needed": true,
  "throughSeq": 423,
  "missed": [
    { "seq": 418, "text": "早捏", "ts": 1795482426432 }
  ],
  "text": "刚看到你前面几条，我这边断线漏掉了，不是故意不理你。上班还顺利吗？",
  "reason": "ok"
}
```

响应（不补）：

```json
{ "ok": true, "needed": false, "reason": "quiet_hours|too_old|cooldown|already_replied|not_master|warming" }
```

### 8.2 `POST /api/memory/catchup/sent`

请求：

```json
{ "chat": "wechat:u:wxid_xxx", "throughSeq": 423, "text": "刚看到……", "result": "submitted" }
```

响应：

```json
{ "ok": true, "recorded": true, "seq": 424 }
```

服务端校验：

- `throughSeq` 必须等于当前 backlog 的最大未回 seq；
- 当前最后一条 assistant 的 seq 必须仍小于 `throughSeq`（否则说明正常回复已经发生，返回 409，桥接丢弃）；
- 幂等：同一 `throughSeq` 已记录过，返回 `already_recorded`。

### 8.3 （可选）`GET /api/memory/backlog`

给启动器/调试用，只读：

```json
{ "ok": true, "chat": "...", "throughSeq": 423, "count": 4, "lastAssistantSeq": 417 }
```

## 9. 状态、幂等与竞态

### 9.1 状态放在 chat.meta

```json
"catchup": {
  "throughSeq": 423,
  "sentAt": 1795497000000,
  "status": "sent|uncertain|skipped|failed",
  "attempts": 1,
  "lastError": ""
}
```

- 放 chat.meta：跟会话一起备份/迁移，不额外维护文件。
- 备份/恢复已覆盖 meta，不需要新目标。

### 9.2 幂等键

`chatId + throughSeq`

- `plan` 时如果 `throughSeq <= meta.catchup.throughSeq`，直接 `already_replied`；
- `sent` 时同 throughSeq 只允许一次；重复请求返回 `already_recorded`。

### 9.3 竞态处理

| 竞态 | 处理 |
|---|---|
| 生成期间用户又发消息 | `plan` 返回的 throughSeq 落后；`sent` 校验失败 → 不记录、不发送；桥接丢弃 |
| 生成期间正常 pipeline 已回复 | `sent` 发现 lastAssistantSeq > throughSeq → 409，丢弃 |
| 桥接重复启动/多实例 | meta 里 throughSeq + sentAt 冷却；第二个实例 `plan` 返回 cooldown |
| 发送结果不确定（submitted） | 标记 `uncertain`，**不重发**；下次启动只提示不自动补 |
| 生成成功但发送失败 | 标记 `failed`，不自动重试；日志 `catchup-send-fail` |

## 10. 桥接侧流程

### 10.1 触发时机

- 桥接启动、UIA 预热完成、`accountOk=true` 后，**等待 20 秒**（让启动期消息先落盘）；
- 每次进程只尝试一次（`self._catchup_done = True`），不随每条消息重复触发；
- Phase 2 可扩展到“UIA 从断开恢复”时触发一次，本方案先不做。

### 10.2 执行步骤

1. 若 `batches`/`pipeline` 有该会话排队消息，或 3 分钟内有新消息 → 跳过；
2. 调 `plan`（超时 15s）；
3. `needed=false` → 记录原因，结束；
4. `needed=true` → 确认当前聊天窗口/发送通道可用（复用 `send_text`/`send_messages`）；
5. 发送（最多 2 个气泡，间隔 300–600ms）；
6. 成功/submitted → 调 `sent` 入记忆；
7. 失败 → 记录日志，**不重试**。

### 10.3 与正常回复的关系

- 补答不是“抢答”：如果用户当前消息在 2 分钟内，根本不触发；
- 补答发出后，用户再回复，走正常 pipeline；backlog hint 会因 assistant 已前移而自动消失。

## 12. 测试计划

### 内核（`鲸鲸-内核自测.js`）

1. `backlog.collect`：只取最后 assistant 之后的 user；当前消息排除；年龄过滤。
2. `plan`：主人私聊 + 2min~6h + 非静默 → needed=true；群聊/陌生人 → false。
3. `plan`：静默时段 → `quiet_hours`；超过 6h → `too_old`；冷却 → `cooldown`。
4. `sent`：正常写入 assistant，throughSeq 前移；重复请求幂等。
5. `sent`：throughSeq 已过期/正常回复已发生 → 409，不写 assistant。
6. 备份/恢复：meta.catchup 保留。

### 桥接（`鲸鲸-自测.py`）

1. UIA 未就绪/预热中 → 不调 plan。
2. plan 返回 needed=false → 不发送。
3. plan needed=true + 发送成功 → 调 sent 一次。
4. 发送失败 → 不调 sent、不重试。
5. 群聊/非主人 → 不触发。
6. 静默时段 → 不触发。

### 端到端（手工/脚本）

- 模拟：kernel 写入 4 条 user（无 assistant），桥接重启，UIA ready；
- 断言：只发 1 次、记忆里新增 1 条 assistant、`meta.catchup.throughSeq` 正确；
- 再重启一次：不再补发。

## 18. 结论

推荐 **方案 C**：桥接触发、内核生成、确认后入记忆；默认只补主人私聊、2 分钟–6 小时、非静默时段、6 小时冷却、每天最多 2 次。  
先 shadow（只 plan 不发送）一天，再打开；任何异常把 `catchup.enabled` 关掉即可回滚。
